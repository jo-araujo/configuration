# Work laptop configuration

## For agents / contributors

- **Layout:** `bin\dev.ps1` is the single interface (`dev help` lists everything; commands live in its `$commands` table). `setup.ps1` runs the steps in `scripts\*.ps1` (`system`, `apps`, `terminal`, `settings`, `git`, `wsl`, `podman`), with shared helpers in `scripts\common.ps1`. Data lives in `apps.json` (winget ids) and `vscode\` (`settings.json`, `keybindings.json`, `extensions.json`; `default.code-profile` is generated by `scripts\export-vscode-profile.ps1`, don't edit it).
- **Constraints:** work laptop, no personal accounts, no GPG keys, no git aliases. Leave Teams and OneDrive alone. Prefer per-user changes over machine-wide ones. Do not add Notepad++, oh-my-posh or Start pins. Steps must be idempotent and runnable on Windows 11 with PowerShell 7. The PowerShell profile is shared by pwsh and Windows PowerShell, so keep it compatible with both. Each setup step keeps its own skip switch in `setup.ps1` and its own `dev setup <step>`. Never copy secrets or machine paths from the live machine into the repo; `vscode\default.code-profile` is the only generated profile file (no readable copy). Failures the user can fix (VS Code open, setting conflicts, app updates) prompt (close/retry/skip, keep/use repo, yes/no); non-interactive runs need explicit flags (`yes`, `-OnConflict`).
- **Gotchas:** a freshly installed tool is not on PATH until `Update-SessionPath`. The Store `python.exe` stubs shadow the real Python. Corporate TLS inspection needs `NODE_OPTIONS=--use-system-ca` for the VS Code CLI. Windows blocks scripted writes to some Explorer keys (`TaskbarDa`). Podman needs a machine (`dev setup podman`). The owner edits `apps.json` and `vscode\` by hand, so re-read before changing them.
- **Verify:** parse-check changed scripts, run `dev help`, and test on temp copies instead of live VS Code settings. Do not run `dev settings sync` with VS Code open without expecting the close prompt.
- **Docs:** update this README whenever a `dev` command or setup step changes.

Run from PowerShell 7 (`winget install Microsoft.PowerShell` if missing):

```powershell
.\setup.ps1                                  # prompts: personal or professional install
.\setup.ps1 -InstallType Professional        # VS Professional, no addons
.\setup.ps1 -InstallType Personal            # VS Community + addons
.\setup.ps1 -SkipWsl                         # skip the Ubuntu/WSL step
.\setup.ps1 -SkipPodman                      # skip the Podman machine (VM) step
```

Other switches: `-SkipSystem`, `-SkipApps`, `-SkipTerminal`, `-SkipVSCode`, `-SkipGit`, `-SkipPodman`. When Ubuntu was just installed and WSL needs a restart, setup asks whether to reboot now; if you decline (or run non-interactively) it skips the Ubuntu `dev` wrapper and the Podman step, so reboot and then run `dev setup wsl` and `dev setup podman`.
- `-SkipTerminal` skips PowerShell/Windows Terminal setup; `-SkipVSCode` skips the independent VS Code settings step. Close VS Code before setup applies its settings.
- The Start menu Recommended section is turned off by `system.ps1`.
- The System step also enables Hibernate, shows it in the power menu, and sets lid-close and a short physical power-button press to Hibernate on both battery and AC for the active power plan. `-SkipSystem` skips this configuration.

### Hibernation permissions

Hibernation configuration is an explicitly machine-wide exception to the per-user preferences and requires an approved elevated PowerShell session. Without elevation, with conflicting enforced policies, or if the device does not support full hibernation, the helper warns and skips/stops that block while the rest of setup continues. It never elevates automatically or edits policy keys.

To rerun only this block from an approved elevated shell:

```powershell
.\scripts\hibernate.ps1
```

Full hibernation uses disk space for `hiberfil.sys`. The helper verifies support and the configured values; a later failure can leave earlier changes applied, which is reported in the warning. It does not hibernate/reboot the machine or change idle timers, the dedicated sleep button, long-press emergency shutdown, or the existing display timeouts. Lid-close settings have no physical effect on devices without lids. Changes apply to the currently active power plan; after switching plans, rerun if needed. Reopen the power menu, or check after a later sign-in, if its Hibernate entry does not refresh immediately.

Windows Terminal uses its default font; setup does not install additional fonts. The PowerShell profile loads posh-git (git completion), and registers tab completion for dotnet, gh (if installed) and `dev`, plus inline suggestions (history, and on PowerShell 7 also the completers via the CompletionPredictor module). After changing repo settings, run `dev settings sync` from an external terminal and restart the shell.

## Sync settings

Run from an external PowerShell or Windows Terminal. If VS Code is open, `sync` and `pull` offer to close it for you (Close / Retry / Skip); from VS Code's own terminal the Close option is hidden because it would kill the shell:

```powershell
git -C C:\dev\jo\configuration pull           # optional, manual repo update
dev settings sync                            # applies this local checkout only
```

`dev settings sync` replaces `dev profile pull`. It works from any directory once `bin\` is on PATH (added by Terminal setup). Before initial setup you can run `.\scripts\settings.ps1` directly. It does not run Git, upload changes, sign in, install shell modules, change PATH, or run the rest of setup.

The same application logic is used by `setup.ps1`. To apply only PowerShell/Terminal or only VS Code:

```powershell
.\scripts\settings.ps1 -SkipVSCode
.\scripts\settings.ps1 -SkipTerminal
```

VS Code settings and shortcuts are **merged**, not replaced: missing repo entries are added and unrelated local entries are preserved. PowerShell profiles, Windows Terminal settings, and Terminal assets are still **replaced** with repo versions. Existing changed files are backed up alongside the destination as `<filename>.<timestamp>.<unique-id>.bak`; unchanged files are left alone. To undo a write, close the affected app and copy the desired backup over the original file. Backups may contain your previous private settings: keep them local. Backups are retained until you remove them. Missing Windows Terminal configuration directories produce a warning; open Windows Terminal once and rerun to apply its settings.

- `vscode\settings.json` and `vscode\keybindings.json` go to `%APPDATA%\Code\User` (local VS Code Stable, Default profile).
- `vscode\extensions.json` lists extension IDs. Missing extensions are installed from the Marketplace at the available version; this requires network access. Already installed extensions are not updated or removed, including any existing .NET extensions. If installation fails, sync reports the failure before replacing settings files; earlier successful extension installs remain installed.
- `terminal\Microsoft.PowerShell_profile.ps1` goes to the user's PowerShell and WindowsPowerShell Documents folders.
- `terminal\settings.json` and image assets update existing Store/unpackaged Windows Terminal installations and `%USERPROFILE%\.config\terminal`.
- `copilot\settings.json` is merged into `%USERPROFILE%\.copilot\settings.json` (`dev setup copilot`, also run by `dev settings sync` and setup unless `-SkipTerminal`); other keys there are kept. `copilot\mcp.example.json` is a copy-only GitHub MCP template: copy it to `.mcp.json` in a project (top-level key `mcpServers`) and sign in with `/mcp auth github`. It is never applied. Keep MCP configs with company URLs (e.g. Azure Boards) out of this repo: put them in a project's `.mcp.json` and add that file to the project's `.git\info\exclude`.

### Merge conflicts

VS Code object settings (including language overrides) merge recursively. Identical values are left alone; different scalar values, arrays, or types are conflicts. Arrays are not concatenated. Existing private settings remain local and are never exported back into the repo.

Shortcuts retain local order, and missing repo shortcuts are appended in repo order without duplicating identical entries. If a local binding uses a repo-managed key but differs in command, condition, arguments, or removal behavior (`-command`), it is a conflict (the tool does not try to prove that different `when` expressions cannot overlap). Choosing the repo side replaces that key's local bindings with the repo ones.

When a conflict is found, interactive sync shows the setting (or shortcut key) with the value on this PC and the value in the repo, and asks: keep local, use repo, keep local for all, use repo for all, or cancel. Nothing is written until every conflict is answered, and overwritten files get a `.bak` backup. Cancelling aborts **before file writes, backups, or extension installs**. Non-interactive runs still stop on conflicts unless you pass `-OnConflict Local` or `-OnConflict Repo` to `scripts\settings.ps1`. Values are printed, so check the repo files contain nothing private. Invalid local JSON also stops the operation.

When new values are merged, existing JSONC files may be reformatted as JSON and comments removed; the backup retains the original. Semantically unchanged files keep their text and comments. Keep VS Code closed throughout the operation. Full `setup.ps1` is not transactional: unrelated setup steps may already have run, and its existing warning/continuation behavior for failed steps remains in effect.

The VS Code baseline is React/JavaScript/TypeScript focused: built-in language support plus ESLint, Prettier, Jest, GitLens, Material Icon Theme, English/Portuguese spell checking, YAML, and Markdown. JS/JSX/TS/TSX use Prettier consistently and respect project configuration; format-on-save is not forced. Jest is for projects that use Jest, not a conversion of other test runners. The active Light Modern theme, portable editor/accessibility preferences, and three custom keybindings are retained. The integrated terminal font has system-font fallbacks; no fonts are installed.

.NET/CSharpier, SQL/Redis connections, Java paths, sandbox filesystem paths, inactive Dracula theme overrides, and unrelated specialist extensions were excluded from the imported VS Code baseline. Existing application installation choices in `apps.json` are unchanged.

### Update the VS Code baseline

Edit the files in `vscode\`, or capture what you changed in VS Code with `dev settings pull`, review the diff, and commit/push manually when desired. On another machine, pull manually and run `dev settings sync`. There is one shared baseline, with no personal/work mode.

`dev settings pull [add|mirror] [yes]` is the reverse of sync: it reads your live VS Code Default profile (settings, keybindings, installed extensions) into `vscode\settings.json`, `keybindings.json` and `extensions.json`. It asks which mode to use unless you pass one: **add** adds new items and updates changed values but never removes anything; **mirror** makes the repo files an exact copy, so settings, keybindings and extensions you removed in VS Code disappear. Each section (settings, keybindings, extensions) shows its diff and asks for confirmation (`yes` skips the questions). Settings and keybindings that look like paths or secrets are never copied and are listed by name only. VS Code can stay open. Nothing is committed; the command offers to regenerate `vscode\default.code-profile`.

To bring preferences from another VS Code installation, open **File > Preferences > Profiles**, select the active profile's **... > Export...**, choose **Settings, Keyboard Shortcuts, Extensions**, and save to a local `.code-profile` file. Review and curate those sections into `vscode\`; do not commit the raw export. Root-level `*.code-profile` exports are ignored because they can contain credentials, private paths, connection data, and extension state. Snippets, tasks, MCP servers, UI/global state, account sessions, and extension storage are not imported.

### Portable profile file

**`vscode\default.code-profile`** is the separate, sanitized, import-compatible snapshot. It contains only the React profile name, settings, keybindings (Windows platform), and extension IDs. The original root-level `default.code-profile` stays ignored and unchanged.

Edit the canonical `vscode\settings.json`, `vscode\keybindings.json`, and `vscode\extensions.json`, then regenerate and review the snapshot:

```powershell
.\scripts\export-vscode-profile.ps1
```

The exporter uses only repo files, not the original export, cloud data, or live user settings. It works from any directory when invoked by its path. No staging, committing, sign-in, or extension installation is performed.

VS Code requires `.code-profile` sections to be serialized strings, so embedded JSON stays escaped even when the outer file is indented. Edit the canonical JSON files, not the snapshot. Formatting is not sanitization: review canonical inputs for secrets before regenerating or publishing.

To import manually, open **File > Preferences > Profiles > New Profile > Import Profile...**, choose `vscode\default.code-profile`, preview it, and create a new profile. Native VS Code import has its own apply/replacement rules and can remove extra extensions from an existing target profile. The file cannot encode our conflict-safe merge policy: use `dev settings sync` for additive merging and preservation of extra extensions.

This is not VS Code's cloud Settings Sync. Separate Microsoft/GitHub sync accounts do not automatically share data. Disable cloud sync for repo-managed categories when using the repo as source of truth, otherwise cloud sync may overwrite applied preferences. No account credentials are transferred or required, apart from whatever authentication/policy your extension Marketplace access requires. Device/company policies are not changed or bypassed.

Named profiles, portable VS Code, Insiders, macOS/Linux, and WSL/SSH/container extension hosts are not supported by this Windows settings command. Run it outside VS Code so the editor cannot overwrite files during synchronization.

## Repository layout

- `apps.json`: winget ids in groups. `core` installs in both modes. Professional adds `business` (Visual Studio Professional, SSMS, IntelliJ IDEA, Postman, Podman CLI, Docker Compose (provider for `podman compose`), Podman Desktop, GitHub Copilot). Personal adds `personal` (Visual Studio Community) and `addons`. The .NET SDK (latest stable) is resolved via winget at run time. Already-installed apps are not upgraded or downgraded. Edit the file to change what installs; no code change is needed.
- PATH and variables like `NVM_HOME` are reloaded after each install and at the start of each step, so new tools work in the same run.
- `scripts\`: one script per step. Git name/email are prompted; no commit signing is configured.
- `terminal\`: PowerShell profile, Windows Terminal settings and images, copied locally with recoverable backups. `vscode\`: curated editor settings, keybindings, extension IDs, and a generated importable profile snapshot. `bin\` is added to the user PATH so `dev` works in cmd, pwsh and Windows PowerShell (and in Ubuntu via a wrapper, from `/mnt/...` paths). Commands (`dev`, `dev alias list`, `dev branch prune`, `dev branch clean`, `dev project clean`, `dev copilot [path]` (starts Copilot CLI in that folder; with no path, pick one of the `C:\dev` folders from a list), `dev setup` (list steps), `dev setup system|apps|vscode|terminal|copilot|git|wsl|podman|all` (run one setup step on its own; `apps` and `all` accept `personal|professional`), `dev apps install|update|list [personal|professional]` (the install type is remembered from setup; `list` shows installed and available versions, `update` shows installed -> new versions and asks to confirm, or pass `yes`), `dev settings pull [add|mirror] [yes]`, `dev settings sync` (Windows only)).
- Widgets can't be turned off by script (Windows protects that setting); turn them off in Settings > Personalization > Taskbar.
- Every step is safe to rerun.
- Most preferences are per-user; hibernation is elevation-gated and machine-wide. Teams, OneDrive and policy settings are left untouched.
